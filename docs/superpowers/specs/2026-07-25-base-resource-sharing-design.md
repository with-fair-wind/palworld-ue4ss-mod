# PalworldEditor 同公会跨据点资源共享设计

## 背景

PalworldEditor 当前能够读取和修改玩家主背包，但尚未解析据点、据点物品存储模块或据点仓库容器。
用户希望增加一个可持久化开关：在单人世界或本地房主环境中，玩家主动建造、制作或修理时，可以直接
消耗同一公会其他据点仓库中的材料。

Palworld 公开类型资料中可以找到以下相关入口：

- `UPalBaseCampManager::GetBaseCampIds` 与 `TryGetModel`；
- `UPalBaseCampModel::GetGroupIdBelongTo`；
- `UPalBaseCampModuleItemStorage::GetContainerIds`；
- `UPalBuilderComponent::CollectItemInfoEnableToUseMaterial` 与
  `IsExistsMaterialForBuildObject`。

这些资料证明游戏具有按据点登记容器以及汇总建造材料的模型，但公开 C++ dump 早于 Palworld 1.0。
实现不能直接复制旧参数布局，必须在 Palworld 1.0 experimental UE4SS + PalSchema 环境中通过运行时反射
验证类、函数、参数和返回值。

参考资料：

- <https://gist.github.com/DRayX/1839565378bc7fb7c92232e25a131d8a>
- <https://github.com/Okaetsu/PalSchema>
- <https://github.com/deafdudecomputers/PalworldSaveTools>
- <https://pwmodding.wiki/>

## 目标

- 在 PalworldEditor GUI 中提供“同公会跨据点资源共享”开关。
- 开关默认关闭，并在退出游戏后保存用户选择。
- 开启后，玩家主动发起的建造、工作台制作和修理可以使用同公会全部据点普通资源仓库中的材料。
- 材料检查与实际扣除使用同一个经过验证的容器集合。
- 优先消耗当前据点材料，再按稳定顺序消耗其他据点材料。
- 不移动物品，不合并或改变箱子界面。
- 所有 Unreal 对象访问只在游戏线程执行，并遵守现有 LoadMap 世界代次边界。
- 任一能力无法可靠验证时安全回退原版行为，不直接修改物品槽位数量。

## 非目标

- 不支持加入其他玩家的多人服务器或未安装本 mod 的专用服务器。
- 不改变箱子浏览、手动存取、帕鲁搬运、食物箱和运输逻辑。
- 不让据点帕鲁自动生产跨据点取材。
- 不跨公会共享资源。
- 不创建全局虚拟仓库，也不搬运或复制实体物品。
- 不实现无限材料、免材料建造或跳过原版材料消耗。
- 不直接读写存档文件。
- 不直接修改 `UPalItemSlot::StackCount` 作为跨据点扣除机制。

## 方案比较

### 方案 A：扩展原版材料容器集合

在建造、制作和修理的材料统计与最终扣除入口中，把原版当前据点容器集合扩展为同公会全部据点资源容器。
原版代码继续负责数量校验、扣除、同步和存档。

优点：

- 不移动实体物品；
- 最大程度复用原版事务与同步逻辑；
- 可以把影响范围限制在玩家主动消耗路径；
- 关闭开关后可以完全恢复原版参数和行为。

缺点：

- 每类操作必须分别确认统计与扣除入口；
- Palworld 版本更新后可能需要重新验证函数签名；
- 若某类操作没有可安全扩展的中心入口，只能暂时禁用该类共享。

### 方案 B：把远端材料临时搬到当前据点

在操作前把材料移动到当前据点，操作后再处理剩余物品。

优点：

- 原版消耗流程无需理解多个据点。

缺点：

- 会改变实际箱子内容；
- 满仓、堆叠限制、筛选箱、崩溃或退出世界可能造成丢失或复制；
- 不符合“不移动物品”的需求。

### 方案 C：修改底层容器查询

让所有据点容器查询全局返回公会级容器集合。

优点：

- 理论覆盖面广。

缺点：

- 可能影响箱子 UI、帕鲁搬运、食物、自动生产和其他系统；
- 很难区分材料消耗与普通容器访问；
- 回归范围过大。

采用方案 A。

## 用户界面与配置

在 PalworldEditor 中新增“据点资源共享”折叠区：

- 复选框：`同公会跨据点资源共享`；
- 状态：关闭、等待进入世界、能力检测中、部分可用、完全可用或不可用；
- 发现统计：同公会据点数量与已验证资源容器数量；
- 子能力：分别显示建造、制作、修理是否可用；
- 错误：显示缺失的类、函数或不兼容参数，不只显示笼统失败。

配置保存在：

```text
ue4ss/Mods/PalworldEditor/config.ini
```

配置键：

```ini
[BaseResourceSharing]
Enabled=false
```

首次运行或配置损坏时使用 `false`。GUI 改变开关后通过临时文件替换方式保存，避免中途写入留下半截配置。
配置只记录用户偏好，不记录任何据点、容器、世界或 UObject 标识。

## 组件设计

### `base_resource_sharing/settings.hpp`

不依赖 Unreal 的配置值对象和解析/序列化逻辑：

- `BaseResourceSharingSettings`；
- 严格解析布尔值；
- 缺失或非法值回退关闭并返回诊断；
- 生成确定性的 INI 文本，便于纯 C++ 测试。

文件路径解析与文件 I/O 留在运行时适配层，不放进纯逻辑头文件。

### `base_resource_sharing/resource_pool.hpp`

不依赖 Unreal 的资源池纯逻辑：

- `BaseId`、`GroupId`、`ContainerId` 的标准库值表示；
- `ContainerDescriptor`：所属据点、公会、容器类型与是否为当前据点；
- 同公会过滤；
- 容器 ID 去重；
- 当前据点优先、其余按据点 ID 和容器 ID 稳定排序；
- 聚合结果与诊断快照。

该组件不保存物品槽位指针，也不执行扣除。

### `base_resource_sharing/pal_base_resources.hpp/.cpp`

Palworld 反射适配层，职责为：

- 解析当前本地玩家和公会 ID；
- 解析当前位置所属据点；
- 从 `UPalBaseCampManager` 枚举据点；
- 通过 `GetGroupIdBelongTo` 只保留当前玩家公会的据点；
- 获取每个据点的 `UPalBaseCampModuleItemStorage`；
- 通过 `GetContainerIds` 获取普通资源容器；
- 把容器 ID 解析为当前帧有效的 `UPalItemContainer`；
- 构造不含 UObject 指针的发现快照；
- 注册与注销每类材料入口 Hook。

所有反射访问与 `ProcessEvent` 只能发生在游戏线程。据点、仓库和玩家等世界实例的 UObject 指针仅在
当前回调内使用。为注销 Hook，可以保存已经验证的稳定 `UFunction` 元数据句柄及其回调 ID；它们不能被
当作世界实例使用，并在函数身份变化时先注销旧 Hook。

### `BaseResourceSharingCoordinator`

由 `PalworldEditorMod` 持有，负责：

- 当前用户开关；
- 当前世界代次；
- Hook 注册状态和回调 ID；
- 建造、制作、修理的独立能力状态；
- Hook 重入保护；
- 向 GUI 发布不含 UObject 指针的状态快照。

能力状态彼此独立。一类入口失败不关闭已经验证成功的其他类型。

## 世界生命周期

Hook 注册仍在 `on_unreal_init()` 之后完成；对象解析只在游戏线程执行。

`LoadMap` 前：

1. 标记共享服务不可访问；
2. 增加现有 `worldGeneration`；
3. 清除据点发现快照和当次 Hook 操作上下文；
4. 让尚未完成的共享请求失效；
5. 保留用户开关偏好，但不执行任何跨据点扩展。

`LoadMap` 后：

1. 允许 EngineTick 重新探测世界对象；
2. 重新验证当前玩家、公会、据点管理器和函数入口；
3. 对已注册且函数身份未变化的 Hook 不重复注册；
4. 若函数身份变化，先注销旧 Hook，再为新的已验证函数注册一次；
5. 所有必需入口验证成功后才把对应子能力标为可用。

mod 卸载时注销所有已注册 Hook。无效 Hook ID 不执行注销。

## 能力检测

每个子能力都必须同时验证：

1. 原版材料统计或可用性检查入口；
2. 原版正式扣除入口；
3. 两个入口使用的容器参数可以安全识别和扩展；
4. 原版扣除仍由游戏完成，不需要直接写槽位；
5. Hook 回调运行在游戏线程；
6. 参数布局与 Palworld 1.0 运行时反射一致；
7. 原版消费顺序与传入容器顺序一致，使“当前据点优先”可以被保证。

只有七项全部通过，该子能力才可启用。

初始候选入口来自公开 dump，但不作为最终 ABI：

- 建造：`UPalBuilderComponent` 的材料收集、存在性检查与服务端建造请求路径；
- 制作：实际 Palworld 1.0 中工作台产品请求所使用的材料统计和扣除路径；
- 修理：实际 Palworld 1.0 中玩家或据点修理请求所使用的材料统计和扣除路径。

制作和修理的精确函数名在实现阶段通过 PalSchema/UHT dump 和 UE4SS 运行时反射确定。若无法确定安全中心入口，
该能力保持不可用；实现不得改用猜测参数布局或直接槽位写入。

## 数据流

开启开关且某子能力可用时：

1. 原版进入材料统计或扣除函数。
2. pre-hook 检查开关、世界状态、子能力状态和重入标记。
3. 解析当前玩家公会和当前据点。
4. 枚举同公会据点及普通资源容器。
5. 对容器 ID 去重，并按当前据点优先的稳定顺序排列。
6. 用扩展后的容器集合替换或补充原函数参数。
7. 原版函数继续执行材料汇总或正式扣除。
8. post-hook 只读取结果、更新诊断并解除重入标记。

统计与扣除必须调用同一套容器发现和排序函数。它们不共享 UObject 指针，但共享纯值规则，避免 UI 显示足够而
实际扣除使用另一套范围。

关闭开关、世界切换、能力不可用或解析失败时，Hook 不修改任何参数，原版函数按当前据点规则执行。

## 容器范围

纳入：

- 当前玩家公会拥有的据点；
- 据点 `ItemStorage` 模块登记的普通资源仓库；
- 当前世界中能够由原版容器管理器成功解析的容器。

排除：

- 其他公会据点；
- 玩家背包和装备容器；
- 掉落物容器；
- 帕鲁容器；
- 食物专用容器；
- 未被据点存储模块登记的场景箱子；
- 无效、重复或处于销毁过程中的容器。

具体容器类型枚举值必须从 Palworld 1.0 dump 或运行时反射确认，不沿用旧 dump 的整数值。

## 重入与并发

- 每类 Hook 使用当前线程的重入深度或等价 RAII guard。
- 内层原版调用检测到 guard 后不再扩展容器集合。
- GUI 线程只修改标准库配置请求，不访问 Unreal。
- 开关变更由 EngineTick 消费；关闭请求优先于后续共享操作。
- 每次回调记录进入时的 `worldGeneration`，返回前发生变化则丢弃诊断更新。
- 单人/本地房主仍按服务端权威路径执行，不为远程客户端注入预测结果。

## 错误处理

- 配置读取失败：使用默认关闭，GUI 显示配置错误。
- 配置保存失败：保留内存中的本次选择，但明确提示未持久化。
- 据点管理器不可用：本帧回退原版，稍后重试发现。
- 玩家或公会不可用：本帧回退原版，不枚举全部世界据点。
- 当前据点不可用：不猜测当前据点；该次操作走原版。
- 容器解析失败：不把该容器加入集合，并在诊断中计数。
- 必需 UFunction 缺失或布局不兼容：对应子能力保持不可用。
- LoadMap：立即停止参数扩展并清理操作上下文。
- Hook 注销失败：记录警告，继续完成 mod 析构；回调首先检查持有者有效标志。

任何错误都不得导致部分人工扣除，因为 mod 不直接逐槽扣减。

## 测试策略

### 纯 C++ 测试

- 默认配置为关闭；
- 合法配置可以往返解析；
- 损坏配置回退关闭并返回诊断；
- 只保留当前公会的据点容器；
- 重复容器 ID 只出现一次；
- 当前据点容器优先；
- 其他据点按稳定 ID 顺序排列；
- 食物、玩家背包和未登记容器被排除；
- 关闭开关时 Hook 参数计划为空；
- 开启但能力不完整时 Hook 参数计划为空；
- 同一调用的重入只扩展一次；
- 旧 `worldGeneration` 的结果不能发布到新世界。

### 构建验证

```powershell
cmake --build --preset ninja-msvc-x64 --target format-check PalworldEditor PalworldEditorTests
ctest --test-dir build --output-on-failure
git diff --check
```

### 游戏内验证

准备同一公会的据点 A 和据点 B：

1. 关闭开关，确认所有行为与原版一致。
2. 据点 A 拥有全部材料，确认建造、制作和修理正常。
3. 据点 B 拥有全部材料，据点 A 没有材料，确认已支持的操作可以执行且只扣 B。
4. A、B 各有部分材料，确认合计足够时可以执行，并优先扣 A。
5. A、B 合计不足，确认原版拒绝操作且没有材料变化。
6. 在箱子界面确认物品没有被提前移动，其他箱子内容不被合并显示。
7. 确认帕鲁搬运、食物箱和自动生产仍只使用所在据点规则。
8. 关闭开关后立即恢复原版范围。
9. 退出世界并重进存档，确认偏好被恢复，但容器重新发现。
10. 在 LoadMap 前后反复切换，确认没有旧容器访问、延迟扣除或崩溃。
11. 创建另一个公会据点，确认其资源从不参与统计或扣除。

纯 C++ 测试不能证明 Palworld 1.0 的材料消费 Hook 正确。每个子能力必须完成对应游戏内端到端验证后，
才能在 GUI 中从“实验性”升级为“可用”。

## 发布与兼容性

- 功能默认关闭。
- README 明确标记仅支持单人世界/本地房主。
- GUI 按建造、制作、修理分别展示兼容状态。
- Palworld 或 PalSchema 更新后重新执行运行时能力检测；检测失败则自动回退原版。
- 第一版不得声称支持专用服务器、远程客户端或所有未来版本。
