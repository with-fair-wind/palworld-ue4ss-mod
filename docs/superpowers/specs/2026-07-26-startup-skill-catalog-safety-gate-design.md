# PalworldEditor 启动阶段技能目录安全门设计

## 背景与证据

PalworldEditor 1.5.2 曾在游戏启动约 8 秒、尚未进入主界面或存档时偶发崩溃。对应 UE4SS 日志显示：

1. `PalworldEditor loaded (v1.5.2)` 和 EngineTick 回调注册成功；
2. 首次背包读取报告 `container not found (not in-game?)`；
3. 物品目录扫描完成；
4. 日志在下一阶段返回前中止，崩溃栈位于 UE4SS EngineTick 回调调用的 Palworld 引擎代码。

第二次及后续启动没有复现，进入存档后帧率和帕鲁编辑均正常。这符合启动画面 UObject 初始化/回收顺序变化导致
的时序竞争。当前首帧流程在玩家 Common 背包容器尚不存在时仍会尝试调用技能目录与本地化 `ProcessEvent`，
这是应消除的无效启动阶段反射；但现有证据不足以断言它是所有启动崩溃的唯一来源。

## 目标

- 玩家 Common 主背包容器可用前，不调用技能目录和技能本地化反射。
- 运行时未就绪时继续使用现有 2 秒自动重试节流，不逐帧探测。
- 手动刷新同样不能绕过运行时安全检查。
- 进入存档且容器可用后，保持现有主动/被动目录、当前语言名称和失败回退行为。
- 不改变 1.5.2 的按需帕鲁解析、250 毫秒目标校验、脏快照发布或据点资源共享。

## 方案选择

### 采用：条件式运行时安全门

技能目录刷新调度器只在刷新到期或收到手动请求时调用一个运行时就绪检查。该检查在 EngineTick 游戏线程即时
解析 Common 主背包容器，只返回布尔值，不缓存 UObject。容器无效时，本次刷新被推迟并安排下一次 2 秒重试；
容器有效时才调用 `PalSkillGateway::load_catalog()`。

这种方案直接检查技能本地化所需的玩家运行时是否存在，既适用于正常启动，也适用于加载较慢和运行中重新注入。

### 未采用：固定启动延时

固定等待若干秒无法覆盖不同机器和 Mod 组合下的加载差异，仍可能过早调用，也会在快速加载时无谓延迟。

### 未采用：只等待首次 LoadMap 后置回调

LoadMap 是有用信号，但不能单独证明本地玩家背包已经建立，也不适合已经进入世界后热加载 Mod 的情况。

## 数据流

1. EngineTick 读取手动刷新标志和当前目录就绪状态。
2. `SkillCatalogRefreshScheduler` 判断本次是否达到刷新时机。
3. 只有达到刷新时机时才调用运行时就绪谓词，避免每帧执行背包反射。
4. 谓词当帧解析 Common 主背包容器：
   - 无效：返回 `false`，不调用 `load_catalog()`；
   - 有效：返回 `true`，执行现有目录加载与分区回退。
5. 目录加载结果继续写入游戏线程工作快照，并仅在 dirty 时发布给 GUI。

## 安全与错误处理

- 安全门和目录加载都只在 EngineTick 游戏线程执行。
- 主背包容器指针只在谓词调用期间使用，不保存到成员、快照或下一帧。
- 手动刷新跳过时间等待，但不跳过运行时安全门。
- 安全门未通过不覆盖已有目录，也不制造新的错误状态；下一次自动重试仍可恢复。
- LoadMap 前后的现有请求清理、目录清空与重新刷新行为保持不变。

## 测试与验收

纯 C++ 回归测试覆盖：

- 运行时未就绪时，刷新调度器拒绝刷新；
- 节流窗口内不重复调用运行时就绪谓词；
- 2 秒后运行时就绪时允许刷新；
- 手动刷新立即检查安全门，但安全门失败时仍拒绝刷新；
- 目录已经就绪且没有手动请求时不调用安全门。

构建验收继续执行：

```powershell
cmake --build --preset ninja-msvc-x64 --target format-check PalworldEditor PalworldEditorTests PalworldEditorBaseResourceSharingTests
ctest --test-dir build --output-on-failure
git diff --check
```

游戏内验收：

1. 连续多次从桌面启动游戏，确认启动画面不再触发技能目录反射崩溃；
2. 进入存档后目录自动加载当前语言名称；
3. 手动刷新、技能编辑和数字键目标检测保持正常；
4. 关闭资源共享时性能与 1.5.2 一致。
